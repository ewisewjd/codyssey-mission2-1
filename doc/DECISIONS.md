# Design Decisions

## DEC-001 — JSONL을 기본 저장 형식으로 선택
- 결정: 거래·카테고리·예산을 각각 JSONL 파일로 저장한다.
- 이유: 표준 라이브러리만으로 구현할 수 있고, 한 줄씩 읽어 제너레이터 스트리밍을 설명하기 쉽다.
- 대안: CSV를 기본 저장 형식으로 사용.
- 장점: 각 행이 독립적인 JSON 객체이며 한 줄 단위 처리에 적합.
- 위험: 손상된 줄 처리와 스키마 변경 정책이 필요하다.
- 검증: 한글 보존, 재실행 후 유지, 잘못된 줄, 빈 파일, update/delete 교체를 테스트한다.

## DEC-002 — 거래 파일과 보조 파일 분리
- 결정: transactions.jsonl, categories.jsonl, budgets.jsonl을 별도로 관리한다.
- 이유: 미션이 최소 3개의 영구 저장 파일을 요구한다.
- 검증: 세 파일이 생성되고 각각의 값이 재실행 후 유지되는지 확인한다.

## DEC-003 — update 방식
- 결정: 옵션 기반 `update --id ID [필드 옵션...]`으로 고정한다.
- 이유: 미션 원문이 허용한 방식 중 평가 시 재현하기 쉽고 자동화 가능한 방식이다.
- 검증: 일부 필드만 수정, 잘못된 필드값, 없는 ID, 수정 후 데이터 보존.

## DEC-004 — 사용 중인 카테고리 삭제
- 결정: 거래에서 참조하는 카테고리는 삭제를 차단하고 사용자에게 원인을 알린다.
- 이유: 기존 거래가 미등록 카테고리를 참조하는 상태를 예방한다.
- 검증: 미사용 카테고리 삭제 성공, 사용 중 카테고리 삭제 거부.

## DEC-005 — ID 생성
- 결정: 충돌 방지 가능한 고유 ID를 생성하고 저장 전에 중복을 확인한다.
- 구현 세부 방식은 코드 작성 시 선택하고 이 문서를 갱신한다.
- 검증: 다수 거래 생성 및 재실행 후에도 ID가 중복되지 않음.

## DEC-006 — 최신순과 스트리밍의 절충
- 결정: 파일을 읽는 경로는 제너레이터를 사용한다. 최신순 출력에 필요한 정렬이 전체 데이터를 메모리에 적재한다면 그 사실을 문서화하고, 구현을 통해 메모리/정렬 요구를 검토한다.
- 이유: 미션이 최신순과 제너레이터 기반 스트리밍을 함께 요구한다.
- 검증: 코드 구조와 데이터 크기별 동작을 확인한다.

## DEC-007 — CSV import 오류 정책
- 결정: 행 단위로 검증하고, 잘못된 행은 오류 이유와 건너뛴 건수를 보고한다. 정상 행을 반영하는 정확한 부분 성공 정책은 구현 전에 확정해 테스트한다.
- 검증: 정상/잘못된 행 혼합 파일과 전체 오류 파일 테스트.
