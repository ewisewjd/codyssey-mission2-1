> 목적: 코드를 통째로 외우는 대신, 이 프로그램이 **무엇을 하는지, 어떻게 동작하는지, 왜 이런 구조를 선택했는지** 이해한다.
>
> 대상: Python 기초 문법을 배우는 중인 학습자. 어려운 용어는 먼저 쉬운 말로 설명하고, 그 다음 실제 코드와 연결한다.

## 이 문서 읽는 법

한 번에 전부 암기할 필요가 없다. 각 장을 읽을 때 다음 세 가지를 표시한다.

- **이해함**: 예제를 보지 않아도 내 말로 설명할 수 있다.
- **다시 읽기**: 대략 뜻은 알지만 코드가 어떻게 이어지는지 모르겠다.
- **질문**: 정확히 이해되지 않는 문장이나 코드 줄을 복사해 질문 목록에 적는다.

이 문서는 기존 주제별 자료를 대체하기보다, 서로 흩어진 개념을 하나의 이야기로 연결하는 중심 문서다. 각 주제의 연습 문제는 [학습 목차](README.md)에서 해당 문서를 찾아 진행한다.

## 1. 먼저 프로그램 전체를 머릿속에 그리기

이 미션은 터미널에서 명령을 받아 거래 내역을 저장하고 검색하는 콘솔 가계부다. 화면에 입력을 받는 코드와 파일을 읽고 쓰는 코드를 한곳에 모두 넣으면 처음에는 쉬워 보여도, 기능이 늘어날수록 고치기 어렵다. 그래서 역할을 나눈다.

```text
사용자
  │ 터미널에 명령 입력
  ▼
__main__.py ── 프로그램 진입점
  ▼
cli.py ─────── 명령/옵션 해석, 입력과 출력, 종료 코드
  ▼
service.py ─── 업무 규칙, 검증, 검색, 합계, CSV 정책
  ▼
storage.py ─── JSONL 파일 읽기/쓰기, 임시 파일 교체
  ▼
data/ ──────── 실제 거래·카테고리·예산 데이터

models.py ──── Transaction 데이터 구조와 입력 검증
decorators.py ─ 실행 시간 측정 같은 공통 기능
```

### 각 파일의 책임

| 파일 | 책임 | 쉽게 말하면 |
|---|---|---|
| `__main__.py` | 프로그램을 시작하고 종료 코드를 전달 | 현관문 |
| `cli.py` | 사용자의 명령과 옵션을 해석하고 화면에 표시 | 접수 창구 |
| `service.py` | 가계부 규칙에 맞게 데이터를 처리 | 업무 담당자 |
| `storage.py` | 파일에서 데이터를 읽고 저장 | 창고 담당자 |
| `models.py` | 거래 데이터의 모양과 검증 규칙 정의 | 거래 양식 |
| `decorators.py` | 함수에 공통 동작을 덧붙임 | 공통 보조 도구 |

예를 들어 사용자가 `python -m budget_app summary --month 2026-10`을 실행하면, CLI가 명령과 월을 해석하고, 서비스가 10월 거래를 계산하며, 저장소가 JSONL 파일에서 거래를 제공하고, CLI가 합계를 화면에 출력한다.

**모듈화의 핵심은 파일 개수를 늘리는 게 아니다. 각 파일이 무엇을 책임지는지 분명하게 만드는 것이다.** CLI를 바꿔도 파일 저장 규칙을 다시 작성할 필요가 없고, 저장 형식을 바꿔도 화면 출력 코드를 전부 고칠 필요가 없도록 경계를 만든다.

## 2. 터미널, 명령어, 리눅스 스타일 옵션

### 2.1 CLI란?

CLI는 Command-Line Interface의 줄임말로, 터미널에 글자로 명령을 입력해 프로그램을 조작하는 방식이다. 이 미션은 웹 화면이나 버튼 대신 터미널을 사용한다.

예시:

```bash
python -m budget_app list --limit 10
python -m budget_app search --category food --type expense
python -m budget_app summary --month 2026-10 --top 5
python -m budget_app export --out october.csv --month 2026-10
```

- `python`: Python 실행기
- `-m budget_app`: `budget_app` 패키지를 모듈 실행 방식으로 실행
- `list`, `search`, `summary`, `export`: 하위 명령
- `--limit 10`, `--month 2026-10`: 명령에 전달하는 옵션과 값

명령은 **무슨 일을 할지**, 옵션은 **그 일을 어떤 조건으로 할지** 지정한다고 생각하면 된다.

### 2.2 `-`와 `--`는 무슨 뜻인가?

명령행 프로그램에서는 관례적으로 짧은 옵션에 `-`, 긴 옵션에 `--`를 사용한다. 이 프로젝트는 긴 옵션 표기를 사용한다.

- `--month 2026-10`: `month` 옵션의 값은 `2026-10`
- `--limit 10`: 최대 10개 표시
- `--type expense`: 지출만 조회
- `--help`: 사용법 안내 요청

이 표기는 Python 문법이 아니라 CLI에서 널리 사용하는 **명령행 표기 관례**다. 옵션을 실제로 읽고 해석하는 역할은 이 프로젝트의 `argparse`가 한다.

### 2.3 `argparse`의 역할

`cli.py`의 `build_parser()`는 명령어와 옵션의 규칙을 정의한다.

```python
parser = argparse.ArgumentParser(prog="python -m budget_app")
commands = parser.add_subparsers(dest="command", required=True)

listing = commands.add_parser("list", help="최신 거래 목록")
listing.add_argument("--limit", type=int, default=20)
```

이 코드의 뜻:

1. 명령행 분석기를 만든다.
2. 하위 명령을 구분할 수 있게 한다.
3. `list`라는 명령을 등록한다.
4. `--limit` 옵션은 정수로 읽고, 생략하면 20을 사용한다.

`argparse`는 `--help` 출력, 필수 옵션 누락, `type=int` 변환 같은 기본 처리를 제공한다. 하지만 날짜가 실제 달력에 존재하는지, 카테고리가 등록되어 있는지 같은 **업무 규칙**은 서비스나 모델의 검증 함수에서 확인해야 한다.

### 2.4 `args`는 무엇인가?

`parser.parse_args()`는 사용자가 입력한 명령행을 해석해 `args` 객체를 만든다. 예를 들어 `list --limit 10`이면 대략 `args.command == "list"`, `args.limit == 10`이 된다. 그 후 `run(args)`가 명령에 맞는 작업을 선택한다.

### 2.5 주요 명령 예시

| 명령 | 하는 일 |
|---|---|
| `add` | 거래 한 건 추가. 필드를 대화형으로 입력 |
| `list --limit 10` | 최신 거래 최대 10건 표시 |
| `search --from 2026-10-01 --to 2026-10-31` | 기간으로 검색 |
| `summary --month 2026-10 --top 3` | 월별 수입·지출·잔액과 지출 상위 3개 |
| `budget set --month 2026-10 --amount 300000` | 월 예산 설정 |
| `category add` | 카테고리 추가 |
| `update --id TX-000001 --amount 9000` | 지정 거래 수정 |
| `delete --id TX-000001` | 지정 거래 삭제 |
| `import --from input.csv` | CSV에서 거래 가져오기 |
| `export --out output.csv --month 2026-10` | 특정 월 거래를 CSV로 내보내기 |

자세한 명령 사용법은 터미널에서 `python -m budget_app --help` 또는 `python -m budget_app list --help`처럼 확인한다.

## 3. 파일 저장: JSON, JSONL, CSV의 차이

파일은 프로그램을 종료해도 데이터가 남도록 해 준다. 변수나 리스트에만 저장한 값은 프로그램이 끝나면 사라지지만, 파일에 기록한 데이터는 다음 실행에서도 읽을 수 있다.

### 3.1 JSON

JSON은 데이터를 표현하는 텍스트 형식이다. 객체는 중괄호, 배열은 대괄호로 표현한다.

```json
{
  "id": "TX-000001",
  "type": "expense",
  "date": "2026-10-29",
  "amount": 5000,
  "category": "food",
  "memo": "점심",
  "tags": ["meal", "lunch"]
}
```

Python의 `json.dumps(value)`는 Python 값을 JSON 문자열로 바꾸고, `json.loads(text)`는 JSON 문자열을 Python 값으로 바꾼다.

### 3.2 JSONL

JSONL은 JSON Lines의 줄임말이다. **한 줄에 JSON 값 하나**, 이 미션에서는 거래 객체 하나를 저장한다.

```text
{"id":"TX-000001","type":"expense","date":"2026-10-29","amount":5000,"category":"food","memo":"점심","tags":["meal"]}
{"id":"TX-000002","type":"income","date":"2026-10-29","amount":3000000,"category":"salary","memo":"월급","tags":[]}
```

각 줄이 독립적인 JSON 객체이므로 한 줄씩 읽고 처리하기 편하다. 이 프로젝트의 기본 저장 형식이다.

### 3.3 CSV

CSV는 행과 열로 데이터를 표현하는 형식이다. 스프레드시트 프로그램과 주고받기에 편리하다.

```csv
date,type,category,amount,memo,tags
2026-10-29,expense,food,5000,점심,"meal,lunch"
2026-10-29,income,salary,3000000,월급,
```

첫 줄은 헤더로, 각 열의 이름을 표시한다. 이 프로젝트는 다음 CSV 스키마를 사용한다.

| 열 | 필수 여부 | 설명 |
|---|---|---|
| `date` | 필수 | `YYYY-MM-DD` 날짜 |
| `type` | 필수 | `income` 또는 `expense` |
| `category` | 필수 | 등록된 카테고리 |
| `amount` | 필수 | 0보다 큰 정수 |
| `memo` | 선택 | 메모 |
| `tags` | 선택 | 쉼표로 구분한 태그 |

CSV의 값에 쉼표나 줄바꿈 등이 들어갈 수 있으므로 문자열을 단순히 `split(",")`해서 모든 CSV를 처리하면 문제가 생길 수 있다. CSV 파일 자체를 읽고 쓸 때는 Python 표준 라이브러리의 `csv` 모듈을 사용한다. 이 프로젝트에서는 태그 필드 안의 여러 태그를 쉼표로 연결하는 별도 규칙을 쓴다.

### 3.4 왜 저장은 JSONL, 입출력은 CSV인가?

- **JSONL**: 거래 한 건의 필드와 태그 목록 같은 구조를 저장하기 편하고 한 줄씩 순차 처리하기 좋다.
- **CSV**: 스프레드시트로 열거나 다른 프로그램과 데이터를 주고받기 편하다.
- **JSON**: 여러 객체를 배열 하나에 묶는 방식도 가능하지만, 이 프로젝트는 거래를 한 줄씩 다루기 위해 JSONL을 선택했다.

확장자는 형식과 역할을 구분하는 단서다. `transactions.jsonl`은 앱 내부 저장용이고, `export.csv`는 내보내기 파일이다.

### 3.5 이 프로젝트에서 실제로 저장하는 파일

기본적으로 `data/` 아래에 다음 파일들이 있다.

- `transactions.jsonl`: 거래
- `categories.jsonl`: 카테고리
- `budgets.jsonl`: 월별 예산
- `transaction_sequence.json`: 다음 거래 ID를 정하기 위한 마지막 번호 기록

거래 데이터와 카테고리·예산을 분리하면 각 종류의 데이터를 따로 읽고 갱신할 수 있다. ID 번호 기록을 별도 파일에 유지하면 가장 최근 거래를 삭제하더라도 같은 ID를 다시 발급하지 않을 수 있다.

## 4. 제너레이터와 스트리밍: 데이터를 하나씩 처리하기

### 4.1 리스트로 한꺼번에 받는 방식

```python
def make_numbers():
    return [0, 1, 2, 3, 4]

numbers = make_numbers()
```

이 함수는 반환하기 전에 리스트를 만든다. 결과가 몇 개 안 되면 편리하지만, 데이터가 아주 많으면 리스트 전체를 메모리에 보관해야 한다.

### 4.2 `yield`를 사용하는 제너레이터

```python
def make_numbers():
    for number in range(5):
        yield number

for number in make_numbers():
    print(number)
```

`yield`는 값을 하나 내보내고 함수의 진행 위치를 기억한다. 다음 값을 요청하면 그 지점부터 이어서 실행한다. 제너레이터는 값을 순차적으로 공급하는 통로처럼 생각할 수 있다.

- `return`: 함수 실행을 끝내고 결과를 돌려준다.
- `yield`: 값을 하나 제공한 뒤 멈춰 있다가 다음 요청 때 이어서 실행한다.

### 4.3 파일을 한 줄씩 읽는 코드

`storage.py`의 핵심 흐름은 다음과 같다.

```python
@staticmethod
def iter_json(path: Path) -> Iterator[dict[str, Any]]:
    if not path.exists():
        return
    with path.open("r", encoding="utf-8") as file:
        for line_number, line in enumerate(file, start=1):
            if not line.strip():
                continue
            yield json.loads(line)
```

실제 코드에는 잘못된 JSON 줄을 사용자에게 이해할 수 있는 오류로 바꾸는 처리도 있다. 여기서 중요한 것은 파일 전체를 한 번에 읽는 `read()` 대신 파일을 줄 단위로 순회한다는 점이다. `iter_transactions()`는 이 결과를 `Transaction` 객체로 변환해 다시 하나씩 제공한다.

### 4.4 스트리밍의 장점과 한계

장점:
- 모든 거래 객체를 처음부터 메모리에 쌓지 않아도 된다.
- 첫 번째 결과를 일찍 처리할 수 있다.
- 데이터를 읽는 코드와 사용하는 코드를 분리하기 쉽다.

한계:
- 한 번 순회한 제너레이터는 끝까지 소비되면 다시 처음부터 자동으로 시작하지 않는다. 다시 읽으려면 새 제너레이터를 만들어야 한다.
- 전체 결과를 정렬하려면 대개 모든 후보를 비교할 수 있도록 데이터를 모아야 한다.
- 스트리밍을 사용했다고 해서 프로그램 전체가 항상 일정한 메모리만 사용하는 것은 아니다. 이후 코드가 리스트로 바꾸면 그 부분에서 메모리를 사용한다.

### 4.5 이 프로젝트는 모든 작업에서 메모리를 똑같이 쓰지 않는다

- `iter_json()`, `iter_transactions()`: 한 줄씩 제공한다.
- `summary()`: 거래를 하나씩 읽으며 합계와 카테고리별 집계를 계산한다.
- `list_transactions(limit)`: 최신 거래 `limit`개를 찾기 위해 `heapq.nlargest`를 사용한다. 전체 거래 목록을 정렬하는 것보다 메모리를 줄일 수 있지만, 결과 `limit`개는 보관한다.
- `search()`: 일치하는 거래를 최신순으로 정렬하기 때문에 검색 결과를 메모리에 모은다.
- `update()`, `delete()`: 파일 전체를 다시 써야 하므로 현재 구현은 남길 거래를 리스트에 모은다. 즉, 읽기는 스트리밍이지만 수정·삭제 전체가 완전한 상수 메모리 방식인 것은 아니다.

**핵심:** 스트리밍은 무조건 모든 데이터를 메모리에 올리는 일을 피하는 기술이지, 정렬이나 전체 파일 교체까지 공짜로 만들어 주는 기술은 아니다.

## 5. 타입 힌트: 코드의 약속을 글로 표시하기

타입 힌트는 변수, 매개변수, 반환값에 어떤 종류의 값을 기대하는지 적는 표기다.

```python
def add_tax(amount: int, rate: float = 0.1) -> float:
    return amount * (1 + rate)
```

- `amount: int`: 정수를 기대한다.
- `rate: float = 0.1`: 기본값이 0.1인 실수 매개변수다.
- `-> float`: 결과가 실수라는 의도를 나타낸다.

미션 코드에서 자주 보이는 타입:

| 표기 | 의미 |
|---|---|
| `str` | 문자열 |
| `int` | 정수 |
| `bool` | 참/거짓 |
| `list[str]` | 문자열 리스트 |
| `dict[str, Any]` | 문자열 키를 가진 딕셔너리, 값의 타입은 다양할 수 있음 |
| `str \| None` | 문자열 또는 `None` |
| `Iterator[Transaction]` | Transaction 객체를 하나씩 제공하는 반복자 |
| `-> None` | 의미 있는 반환값이 없음 |

### 타입 힌트가 검증을 대신하지 않는 이유

```python
def spend(amount: int) -> None:
    print(amount)

spend("많이")
```

Python은 기본적으로 이 호출을 실행 시 자동으로 거부하지 않는다. 타입 힌트는 주로 사람과 IDE, 정적 타입 검사 도구가 코드를 이해하는 데 도움을 준다. 실제 입력이 올바른지는 검증 코드가 확인해야 한다.

그래서 이 프로젝트는 `validate_transaction_fields()`에서 거래 종류, 날짜, 금액, 카테고리를 실제로 검사한다. 타입 힌트는 “어떤 값을 기대하는가”를 표현하고, 검증 함수는 “실제로 조건을 만족하는가”를 확인한다.

### `Any`와 `object`는 왜 보일까?

- `Any`: 여러 종류의 값을 허용하며 타입 검사 도구가 세부 검사를 제한적으로 수행하도록 한다.
- `object`: Python의 거의 모든 값을 담을 수 있는 일반 타입이다. `Any`보다 안전하게 다루려면 사용하기 전에 실제 타입을 확인해야 한다.

타입 힌트는 문서이자 도구다. 주석처럼 설명을 제공하지만, 주석과 달리 IDE의 자동완성과 타입 검사에 활용될 수 있다.

## 6. 클래스, dataclass, self, cls

### 6.1 클래스와 인스턴스

클래스는 데이터와 관련 동작을 묶는 설계도이고, 인스턴스는 그 설계도로 만든 실제 객체다.

```python
class Dog:
    def __init__(self, name: str) -> None:
        self.name = name

dog = Dog("초코")
print(dog.name)
```

`dog`는 인스턴스다. `self`는 지금 작업 중인 그 인스턴스를 가리킨다. `self.name = name`은 전달받은 이름을 해당 객체의 속성으로 저장한다.

### 6.2 `@dataclass`

미션의 `Transaction`은 다음과 같은 데이터 구조다.

```python
@dataclass
class Transaction:
    id: str
    type: str
    date: str
    amount: int
    category: str
    memo: str = ""
    tags: list[str] = field(default_factory=list)
```

`@dataclass`는 필드 선언을 바탕으로 `__init__()`, 보기 편한 `__repr__()` 등 반복적인 코드를 자동 생성한다. 따라서 객체를 만들 때 `Transaction(id=..., type=..., ...)`처럼 쓸 수 있다.

`memo: str = ""`는 메모를 생략하면 빈 문자열을 사용한다. 하지만 리스트 같은 변경 가능한 기본값을 여러 객체가 공유하면 문제가 생길 수 있다. `field(default_factory=list)`는 객체를 만들 때마다 새 리스트를 생성한다.

### 6.3 `@classmethod`와 `@staticmethod`

이름은 비슷하지만 목적이 다르다.

- 일반 인스턴스 메서드: 첫 인수로 `self`를 자동 전달받아 해당 객체를 다룬다.
- `@classmethod`: 첫 인수로 클래스 자체인 `cls`를 자동 전달받는다.
- `@staticmethod`: `self`나 `cls`를 자동 전달받지 않는다. 전달한 인수만으로 동작한다.

`Transaction.from_dict(cls, data)`는 딕셔너리를 받아 `cls(...)`로 객체를 만든다. 따라서 클래스 메서드가 적합하다. `JsonlStore._atomic_write(path, rows)`는 전달된 경로와 행만으로 작업하고 저장소 인스턴스의 상태가 필요하지 않으므로 정적 메서드로 선언했다.

## 7. 데코레이터: 기존 함수에 공통 동작을 덧붙이기

### 7.1 왜 쓰는가?

여러 함수의 실행 시간을 재거나 로그를 남기고 싶다고 하자. 각 함수 안에 똑같은 측정 코드를 반복해서 넣으면 중복이 생긴다. 데코레이터는 원래 업무와 반복적인 보조 기능을 분리하는 방법이다.

### 7.2 가장 작은 데코레이터

```python
def announce(function):
    def wrapper():
        print("시작")
        result = function()
        print("끝")
        return result
    return wrapper

@announce
def hello():
    print("안녕")

hello()
```

`@announce`는 개념적으로 `hello = announce(hello)`와 비슷하다. 원래 함수 `hello`를 `announce`에 전달하고, 돌려받은 `wrapper`가 이후 호출을 맡는다.

### 7.3 매개변수를 받는 데코레이터

프로젝트에는 다음과 같은 코드가 있다.

```python
@timed("명령 실행")
def run(args: argparse.Namespace) -> int:
    ...
```

여기서 `"명령 실행"`은 원래 함수 `run`의 인수가 아니라 데코레이터가 출력할 라벨이다. 그래서 함수가 세 겹으로 보인다.

1. `timed("명령 실행")`: 라벨을 받는다.
2. `decorate(function)`: 실제로 감쌀 함수를 받는다.
3. `wrapper(*args, **kwargs)`: 나중에 원래 함수가 호출될 때 인수를 전달하고 실행 시간을 측정한다.

`*args`는 위치 인수 여러 개, `**kwargs`는 이름을 지정한 인수 여러 개를 받는다. `functools.wraps(function)`은 감싼 함수의 이름과 문서 같은 정보를 원래 함수에 가깝게 보존하도록 돕는다.

현재 `timed`는 환경 변수 `BUDGET_APP_SHOW_TIMING=1`일 때만 시간을 출력한다. 원래 함수가 예외를 일으키면 현재 코드는 시간 출력 줄에 도달하지 않는다. 성공과 실패 모두 시간을 측정하려면 `try/finally`를 사용하는 설계를 고려할 수 있다.

### 데코레이터를 쓸 때 주의할 점

- 원래 함수의 인수와 반환값을 제대로 전달해야 한다.
- 예외를 무조건 삼키면 실제 오류를 숨길 수 있다.
- 공통 기능을 분리하되, 코드 흐름이 너무 복잡해지지 않도록 한다.
- 데코레이터가 있다고 해서 오류 처리가 자동으로 완벽해지는 것은 아니다.

## 8. 기능이 계층 사이를 이동하는 방법

### 8.1 거래 추가 `add`

1. `cli.py`가 사용자의 입력을 받는다.
2. 금액 문자열이 양의 정수인지 기본 검사를 한다.
3. `service.py`의 `BudgetService.add()`가 거래 필드를 검증하고 카테고리 존재 여부를 확인한다.
4. `models.py`의 `Transaction` 객체를 만든다.
5. 저장소가 거래 ID를 발급하고 JSONL 파일에 한 줄을 추가한다.
6. CLI가 생성된 ID를 표시한다.

입력은 먼저 문자열로 들어올 수 있다. 그래서 금액을 `int`로 변환하고, 0보다 큰지 확인한다. 사용자가 잘못된 값을 입력할 수 있으므로 검증은 반드시 필요하다.

### 8.2 목록 `list`와 검색 `search`

목록은 최근 거래를 제한된 개수만 보여준다. 검색은 날짜, 카테고리, 유형, 메모 키워드, 태그 같은 조건을 적용한다. `filtered()`는 조건에 맞는 거래를 `yield`로 제공한다.

- `list_transactions()`: 최신 거래 중 최대 N개를 선택한다.
- `search()`: 조건에 맞는 거래를 모두 찾은 다음 최신순으로 정렬한다.

날짜가 `YYYY-MM-DD` 형식이면 연·월·일 순서로 고정되어 있어 문자열 비교가 날짜 순서와 일치한다. 단, 이 장점은 날짜 형식을 엄격히 검증했을 때 성립한다.

### 8.3 월별 요약 `summary`

서비스는 월이 일치하는 거래를 순회하면서 수입과 지출을 누적한다.

- 잔액 = 총수입 - 총지출
- 지출 카테고리별 합계 = 카테고리마다 지출 금액을 더한 값
- TOP N = 지출 합계가 큰 카테고리 N개

`Counter`는 항목별 개수를 세거나 합계를 모으는 데 편리한 자료구조다. 예산이 있으면 CLI가 지출 ÷ 예산 × 100으로 사용률을 계산한다.

### 8.4 수정 `update`와 삭제 `delete`

현재 구현은 JSONL 파일의 중간 한 줄을 직접 편집하지 않는다. 수정/삭제 대상과 남길 데이터를 읽고, 새로운 전체 파일을 만들어 원본과 교체한다. 안전한 파일 교체는 10장에서 자세히 설명한다.

## 9. JSONL ↔ CSV 내보내기와 가져오기

### 9.1 Export

Export는 앱 내부의 거래를 CSV 파일로 내보내는 기능이다. 사용자는 `--month` 또는 `--from`과 `--to`로 범위를 지정한다.

1. 필터 조건이 있는지 확인한다.
2. 월/날짜 형식과 시작일·종료일 관계를 검증한다.
3. 임시 CSV 파일을 만든다.
4. 헤더와 거래 행을 기록한다.
5. 기록을 마무리한 후 임시 파일을 최종 경로로 교체한다.

왜 조건을 파일 열기 전에 검증할까? `filtered()`는 제너레이터이므로 함수 호출만으로 내부 코드가 전부 실행되지 않는다. 순회가 시작되어야 검증이 실행될 수 있다. 목적 파일을 먼저 열어버리면, 잘못된 필터를 발견하기 전에 기존 파일을 건드릴 위험이 있다.

### 9.2 Import

Import는 외부 CSV의 거래를 앱에 추가한다.

1. `utf-8-sig`로 파일을 열어 UTF-8 BOM이 있는 파일도 읽는다.
2. `csv.DictReader`로 헤더와 행을 읽는다.
3. 필수 헤더가 있는지 확인한다.
4. 각 행의 금액과 필드를 검증한다.
5. 유효한 행은 일반 `add()`를 재사용해 저장한다.
6. 잘못된 행은 건너뛰고 행 번호와 오류 이유를 모은다.

현재 정책은 **부분 성공**이다. 예를 들어 1~3행은 저장되고 4행이 잘못되었다면, 1~3행은 그대로 남고 4행은 건너뛴다. 전체 CSV가 완벽할 때만 전부 반영하고 오류가 하나라도 있으면 전부 되돌리는 방식은 아니다. CLI는 건너뛴 행이 있으면 종료 코드 1을 반환한다.

가져오기를 다시 실행하면 같은 CSV의 거래가 중복 추가될 수 있다. 현재 구현에는 CSV 행의 중복을 자동으로 판별해 차단하는 일반적인 중복 방지 장치가 없으므로 주의한다.

## 10. 파일 안전성: 임시 파일, rename, 원자성

이 장은 동료평가에서 설명하기 좋은 핵심 설계다.

### 10.1 원본 파일을 직접 덮어쓰면 어떤 문제가 생길까?

파일을 비운 다음 새 내용을 쓰는 도중 프로그램이 종료되거나 디스크 오류가 나면, 원본 파일이 비었거나 일부 내용만 남을 수 있다. 수정이나 삭제처럼 전체 파일을 다시 만드는 작업에서 특히 위험하다.

### 10.2 임시 파일에 먼저 쓰기

현재 저장소의 `_atomic_write()`는 다음 순서로 작동한다.

1. 원본과 같은 디렉터리에 임시 파일을 만든다.
2. 새 내용을 임시 파일에 모두 쓴다.
3. `flush()`로 Python 버퍼에 남은 내용을 밀어낸다.
4. `os.fsync()`로 운영체제에 파일 데이터를 저장 장치에 기록하도록 요청한다.
5. 파일을 닫는다.
6. `os.replace(temp_name, path)`로 임시 파일을 최종 경로와 교체한다.
7. 교체 전에 오류가 났다면 `finally`에서 임시 파일을 정리한다.

같은 디렉터리에 임시 파일을 만드는 이유는 보통 같은 파일 시스템 안에서 교체할 수 있게 하기 위해서다. `os.replace()`는 기존 목적 파일이 있으면 교체한다.

### 10.3 원자성이란?

원자적 작업은 관찰하는 쪽에서 중간의 불완전한 상태가 드러나지 않도록 한 번에 적용되는 것처럼 보이는 작업이다. 파일 교체의 경우, 새 파일을 완성한 뒤 교체하므로 원본 파일을 직접 비우고 다시 쓰는 것보다 부분 기록 위험이 작다.

다만 정확한 보장 범위를 과장하면 안 된다.

- 임시 파일을 완성하기 전에 실패하면 원본 파일은 보통 그대로 남는다.
- 교체가 성공하면 최종 경로는 새 파일을 가리킨다.
- 이것만으로 여러 프로세스가 동시에 같은 파일을 수정하는 충돌이 해결되지는 않는다.
- `fsync`는 파일 데이터에 대한 저장 요청이며, 모든 파일 시스템과 하드웨어에서 모든 종류의 전원 장애를 완벽히 막는다는 뜻은 아니다.
- 여러 데이터 파일을 한꺼번에 교체하는 다중 파일 트랜잭션과도 다르다.

### 10.4 파일 기반 트랜잭션 사고

데이터베이스는 트랜잭션을 통해 여러 변경 작업을 묶고 실패 시 되돌리는 기능을 제공할 수 있다. 단순 파일 기반 프로그램에는 그런 기능이 자동으로 생기지 않는다. 그래서 “검증을 먼저 하고, 새 내용을 별도 파일에 완성하고, 마지막에 교체한다”는 설계로 위험을 줄인다.

현재 `update()`는 모든 검증과 ID 존재 확인이 끝난 후에만 저장소 교체를 호출한다. 대상 ID가 없거나 검증이 실패하면 교체를 호출하지 않는다. `delete()`도 대상이 없으면 파일을 다시 쓰지 않는다.

## 11. 예외, 스택트레이스, 종료 코드

### 11.1 예외란?

예외는 프로그램 실행 중 정상적인 흐름으로 처리하기 어려운 문제가 발생했음을 알리는 Python의 방식이다. 예를 들어 날짜 형식이 잘못되었거나 파일이 없거나 JSON 문법이 깨졌을 때 예외가 발생할 수 있다.

```python
try:
    amount = int(amount_text)
except ValueError:
    print("금액은 정수로 입력하세요.")
```

`try` 안의 작업이 실패하면 해당 예외에 맞는 `except` 블록으로 이동한다. 다만 모든 오류를 무조건 잡아서 무시하면 버그가 감춰질 수 있다.

### 11.2 스택트레이스란?

스택트레이스(traceback)는 오류가 발생했을 때 어떤 함수가 어떤 함수를 호출했는지, 어느 파일의 어느 줄에서 문제가 발생했는지 보여주는 추적 정보다. 개발자가 원인을 찾을 때 매우 유용하지만, 일반 사용자에게는 길고 이해하기 어려울 수 있다.

이 미션은 최종 사용자가 스택트레이스 대신 원인과 해결 힌트를 보도록 한다. `main()`은 예상 가능한 `ValueError`, `OSError`, `KeyError` 등을 처리해 메시지를 출력한다. 그러나 예상하지 못한 모든 종류의 버그를 무조건 숨기는 것이 목표는 아니다. 개발 중에는 전체 오류 정보를 확인할 수 있는 방법도 필요하다.

### 11.3 종료 코드

프로그램은 종료할 때 정수를 운영체제에 반환할 수 있다.

- `0`: 보통 정상 완료
- `0`이 아닌 값: 오류 또는 일부 실패

이 프로젝트는 `main()`이 종료 코드를 반환하고, `__main__.py`에서 `raise SystemExit(main())`로 그 값을 프로세스 종료 상태에 전달한다. CSV 가져오기는 일부 행을 건너뛰면 1을 반환하므로, 명령이 실행되었더라도 결과가 완전하지 않았음을 자동화 도구가 알 수 있다.

### 11.4 `KeyboardInterrupt`와 `EOFError`

- `KeyboardInterrupt`: 사용자가 보통 Ctrl+C로 실행을 중단할 때 발생한다.
- `EOFError`: 입력을 기다리는 중 더 이상 입력을 받을 수 없을 때 발생할 수 있다.

이 프로젝트는 두 상황을 사용자 메시지와 종료 코드로 처리한다.

## 12. 콘솔 출력 포맷과 문자열 정렬

데이터를 올바르게 계산하는 것과 보기 좋게 표시하는 것은 서로 다른 책임이다. 계산 로직이 화면 문자열을 직접 조립하기 시작하면 출력 모양을 바꿀 때 업무 로직까지 건드리기 쉬워진다.

### 12.1 f-string의 폭과 정렬

```python
name = "expense"
print(f"{name:<10}")   # 왼쪽 정렬, 최소 폭 10
print(f"{name:>10}")   # 오른쪽 정렬, 최소 폭 10
print(f"{name:^10}")   # 가운데 정렬, 최소 폭 10
print(f"{12500:>10,}") # 천 단위 구분 기호와 오른쪽 정렬
```

- `<`: 왼쪽 정렬
- `>`: 오른쪽 정렬
- `^`: 가운데 정렬
- 숫자 뒤의 쉼표 `,`: 천 단위 구분 표시

폭은 최소 폭이다. 값이 더 길면 자동으로 잘라내지 않는다. 또한 터미널에서 한글은 글자당 표시 폭이 영문과 다를 수 있어 단순한 문자열 길이만으로 완벽하게 표를 맞추기 어렵다.

### 12.2 출력 포맷터를 분리한다는 뜻

`service.py`는 거래를 찾고 계산하는 데 집중하고, CLI나 별도 포맷터 함수가 거래를 사람이 읽기 좋은 문자열로 만든다. 예를 들어 `format_transaction(item)` 같은 함수를 만들면 출력 모양을 한곳에서 수정할 수 있다.

현재 `cli.py`의 `print_transactions()`는 구분 기호를 사용해 각 거래를 출력하지만, 모든 열의 폭을 고려한 완전한 표 레이아웃은 아니다. 따라서 **기본 출력은 존재하지만, 정교한 테이블 정렬은 별도 개선 항목**으로 이해해야 한다.

## 13. 백업과 복원: 현재 기능과 설계할 때의 주의점

백업은 현재 미션에서 보너스로 제시된 기능이다. 현재 앱에 타임스탬프 백업과 복원 명령이 완성되어 있다고 가정하면 안 된다. 이 장은 기능을 추가한다면 무엇을 고려해야 하는지 설명한다.

### 13.1 타임스탬프 파일명

예를 들어 `backup-20261029-134500/`처럼 날짜와 시간을 포함하면 여러 백업을 구분하기 쉽다. 타임스탬프는 파일을 만든 시각을 나타내는 이름 규칙일 뿐, 백업 내용이 정상인지 자동으로 보증하지는 않는다.

### 13.2 무엇을 백업해야 하나?

거래 파일만 복사하고 카테고리나 예산 파일을 빼면, 복원 후 데이터가 서로 맞지 않을 수 있다. 적어도 거래·카테고리·예산·거래 ID 시퀀스 파일처럼 프로그램 상태에 영향을 주는 파일을 함께 고려해야 한다.

### 13.3 안전한 백업/복원 흐름

1. 백업 대상 파일 목록을 정한다.
2. 타임스탬프가 포함된 별도 백업 경로를 만든다.
3. 파일을 복사한다.
4. 필요한 파일이 모두 존재하고 크기 등 기본 검증을 통과했는지 확인한다.
5. 복원 전에는 현재 데이터를 별도로 보존한다.
6. 복원할 백업 파일이 올바른 형식인지 확인한 뒤 적용한다.
7. 복원 후 목록과 요약이 정상 작동하는지 확인한다.

백업은 복사만 하는 기능이 아니라, 실제로 되돌릴 수 있는지 검증해야 가치가 있다. 개인 가계부 데이터에는 민감한 정보가 포함될 수 있으므로 백업 파일을 공개 Git 저장소에 올리지 않는다.

## 14. 반복 거래: 월급과 월세를 규칙으로 표현하기

반복 거래 역시 현재 앱에 완성된 기능으로 들어 있다고 가정하면 안 되는 보너스 주제다. 반복 거래를 구현한다면 “이번 달 거래를 그냥 하나 더 추가한다”가 아니라, 규칙에 따라 어떤 거래를 생성할지 명확하게 정의해야 한다.

### 14.1 규칙에 필요한 정보

예를 들어 월세 규칙은 다음 정보를 가질 수 있다.

- 이름: 월세
- 유형: 지출
- 금액: 500000
- 카테고리: rent
- 매월 생성할 날짜: 25일
- 시작 월과 종료 월
- 메모와 태그

월급도 비슷하지만 유형은 수입이고 카테고리는 salary가 될 수 있다.

### 14.2 예외 상황

- 31일이 없는 달에 31일 규칙은 어떻게 처리할까? 해당 월 마지막 날로 맞출지, 생성을 건너뛸지 정책을 정해야 한다.
- 같은 달에 명령을 두 번 실행하면 중복 거래가 생기지 않게 해야 한다.
- 규칙이 변경되었을 때 과거 거래까지 바꿀 것인지, 이후 생성분에만 적용할 것인지 정해야 한다.
- 생성된 거래가 어느 반복 규칙에서 왔는지 추적할 ID나 출처 정보가 필요할 수 있다.

**자동 생성은 날짜 계산보다 중복 방지와 예외 정책이 더 중요할 수 있다.** 구현 전에 정책을 글로 정하고 테스트 사례를 만들어야 한다.

## 15. 동료평가에서 설명할 수 있어야 할 핵심 답변

### Q1. 왜 JSONL을 선택했나요?

JSONL은 한 줄에 거래 하나를 저장하므로 파일을 한 줄씩 읽을 수 있고, 각 거래의 필드와 태그 목록을 구조화해 보관하기 편합니다. CSV는 스프레드시트와 호환성이 좋아 외부 입출력에 사용했습니다.

### Q2. 제너레이터를 사용하는 이유는 무엇인가요?

`yield`로 값을 하나씩 제공하면 전체 거래를 한 번에 리스트로 만들지 않고 순차 처리할 수 있습니다. 다만 최신순 정렬이나 수정·삭제처럼 전체 데이터가 필요한 작업은 메모리를 사용할 수 있으므로 모든 기능이 완전한 스트리밍이라고 말하면 안 됩니다.

### Q3. 타입 힌트가 입력 오류를 막아 주나요?

자동으로 막아 주지는 않습니다. 타입 힌트는 함수가 기대하는 값의 종류를 표현하고 IDE와 정적 검사 도구를 돕습니다. 실제 날짜, 금액, 카테고리의 유효성은 별도 검증 코드가 확인합니다.

### Q4. 데코레이터를 사용하는 이유는 무엇인가요?

실행 시간 측정이나 로그 같은 공통 동작을 원래 업무 함수에서 분리해 중복을 줄이고 재사용하기 위해 사용합니다. 이 프로젝트의 `@timed`는 환경 변수가 켜졌을 때 명령 실행 시간을 표시합니다.

### Q5. 수정과 삭제는 어떻게 데이터를 보호하나요?

원본 파일을 직접 부분 수정하지 않고, 검증을 통과한 새 거래 목록으로 임시 파일을 완성한 뒤 `os.replace()`로 교체합니다. 쓰기 중 실패해 원본이 부분적으로 덮어써질 위험을 줄입니다. 다만 동시 수정 충돌이나 여러 파일을 한꺼번에 바꾸는 트랜잭션까지 해결하는 것은 아닙니다.

### Q6. CSV 가져오기는 전부 성공하거나 전부 실패하나요?

아닙니다. 현재 구현은 유효한 행을 저장하고 잘못된 행은 건너뛰는 부분 성공 방식입니다. 건너뛴 행이 있으면 오류 목록을 출력하고 종료 코드 1을 반환합니다.

### Q7. 스택트레이스는 무엇인가요?

오류가 발생하기까지 거친 함수 호출과 파일·줄 번호를 보여 주는 정보입니다. 개발자가 디버깅할 때 유용하지만 일반 사용자에게는 복잡할 수 있어, 예상 가능한 오류는 원인과 해결 힌트로 안내합니다.

### Q8. 백업과 반복 거래는 구현되어 있나요?

미션에서 보너스로 제시된 기능입니다. 현재 코드의 기본 기능과 구분해야 합니다. 백업을 추가한다면 여러 데이터 파일의 일관성 및 복원 검증을, 반복 거래를 추가한다면 월말 날짜 처리와 중복 생성을 특히 고려해야 합니다.
