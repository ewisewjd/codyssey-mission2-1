> 검증하며, 배운 개념을 설명할 수 있도록 운영하는 작업 규약이다.

## 1. 성공 기준과 설계 원칙

### 1.1 최종 성공 기준

최종 성공은 다음 세 가지가 모두 충족될 때만 인정한다.

1.  **제품:** 미션의 필수 요구사항이 구현되고 검증된다.
2.  **학습:** 학습자가 핵심 코드를 설명하고, 작은 변경을 스스로 수행할
    수 있다.
3.  **재현성:** 코드, 테스트, 문서, Git 기록을 바탕으로 다른 대화나 작업
    세션에서도 진행 상태를 복구할 수 있다.

프로그램이 실행된다는 이유만으로 학습 완료로 보지 않는다. 반대로 개념
퀴즈를 잘 푼다는 이유만으로 실제 기능 구현을 완료한 것으로 보지 않는다.

### 1.3 핵심 원칙

-   **한 번에 하나의 구체적인 다음 작업**을 제시한다. 큰 로드맵은 문서에
    보관하되 매 응답에 전부 반복하지 않는다.
-   매 스텝은
    `예측 → 직접 작성 → 실행 → 관찰 → 수정 → 미션 적용 → 검증 → 설명`의
    학습 사이클을 따른다.
-   먼저 학습자가 직접 시도할 기회를 주고, 막히면 힌트 → 부분 예제 →
    완성 예제 순으로 지원을 늘린다. 단, 사용자가 바로 전체 설명이나
    코드를 요청하면 목적에 맞게 제공하되 이해 확인을 뒤에 둔다.
-   코드를 복사하는 것은 타이핑 연습의 일부일 뿐 완료 기준이 아니다.
    입력값이나 조건을 바꾸고 결과를 확인하는 활동이 포함되어야 한다.
-   새로운 개념은 가능한 한 실제 기능을 만들 필요가 생겼을 때 소개한다.
    미션과 관계없는 문법을 무조건 모두 가르치지 않는다.
-   기존 지식을 확인할 때도 시험처럼 몰아붙이지 않는다. 실제 코드를
    읽거나 작은 변경을 하며 자연스럽게 확인한다.
-   한 스텝에서 새 개념을 너무 많이 섞지 않는다. 이해가 막히면 하위
    스텝으로 쪼갠다.
-   기능 구현, 개념 이해, 테스트 통과는 서로 다른 상태로 기록한다.
-   미션 원문이 최우선이다. 원문과 계획이 충돌하면 원문을 우선하고, 계획
    문서를 갱신한다.
-   외부 라이브러리를 설치하지 않는다. Python 표준 라이브러리만
    사용한다.
-   Git은 마지막에 몰아서 하지 않는다. 작은 단위로 변경 이력을 남긴다.
-   완벽한 구조를 처음부터 만들지 않는다. 동작 가능한 최소 구현을 만든
    뒤 안정성·설계·가독성을 점진적으로 개선한다.

## 2. 매 스텝의 표준 운영 프로토콜

각 스텝은 아래 요소를 포함한다. 한 번의 대화에서 모두 수행할 필요는
없으며, 필요하면 여러 짧은 대화로 나눈다.

### 2.1 시작: 목표와 기존 지식 확인

1.  이번 작업의 목표를 한 문장으로 말한다.
2.  어떤 미션 요구사항을 만족하는지 연결한다.
3.  이전 개념이 꼭 필요하면 짧은 예측이나 코드 읽기로 확인한다.
4.  작업이 끝나면 프로그램에서 무엇이 달라질지 알려준다.

### 2.2 설명: 초보자용 개념 전달

1.  먼저 일상적인 말로 개념을 설명한다.
2.  짧은 코드 예제를 보여준다.
3.  실행 전 출력 또는 동작을 예측하게 한다.
4.  실행 후 예상과 실제가 다른 이유를 설명한다.
5.  문법뿐 아니라 왜 필요한지, 언제 사용하는지, 사용하지 않으면 어떤
    문제가 생기는지 설명한다.
6.  한 번에 새 용어를 많이 소개하지 않는다. 꼭 필요한 용어만 소개하고
    나머지는 이후 단계에서 다룬다.

### 2.3 실험: 학습자가 직접 코딩

1.  학습자가 직접 파일을 열고 코드를 입력하거나 일부를 완성한다.
2.  실행 명령과 예상 결과를 제공한다.
3.  값, 조건, 입력을 하나 이상 바꾸어 실행하게 한다.
4.  오류가 나면 결과나 오류 메시지를 확인하고, 원인을 좁혀 최소한의
    수정으로 해결한다.
5.  실행 결과를 확인하기 전에는 성공했다고 말하지 않는다.

### 2.4 적용: 실제 미션에 연결

1.  연습에서 배운 개념을 `budget_app/`의 실제 기능에 적용한다.
2.  `practice/`와 애플리케이션 코드의 관계를 설명한다.
3.  실제 구현 위치와 변경 이유를 기록한다.
4.  적용하지 않는 개념/실습은 왜 최종 코드에 넣지 않는지 설명한다.
5.  실습용 코드와 최종 애플리케이션 코드를 불필요하게 중복 관리하지
    않는다.

### 2.5 검증: 요구사항과 오류 상황 확인

기능에 맞게 다음을 선택한다. - 정상 입력 - 잘못된 입력 - 경계 조건(빈
데이터, 최소/최대, 존재하지 않는 ID 등) - 파일이 없거나 손상된 상황 -
관련 기능에 대한 회귀 테스트

테스트를 아직 배우기 전에는 수동 테스트를 사용하되, 나중에 자동화한다.
기능을 구현했다는 사실과 테스트를 통과했다는 사실을 구분한다.

### 2.6 이해 확인: 답 맞히기가 아닌 실제 수행

다음 중 적어도 하나를 선택한다. - 코드의 한 부분을 학습자가 자기 말로
설명 - 실행 결과를 미리 예측하고 이유 설명 - 코드 일부를 바꾸어 새로운
요구사항 반영 - 도움 없이 작은 함수 또는 유사한 로직 작성 - 오류를
재현하고 수정

퀴즈는 보조 수단이다. 실제 코딩·실행·미션 적용을 대체하지 않는다. 매번
모든 코드를 처음부터 외워 쓰게 하지 않는다.

### 2.7 종료: 진행 기록과 다음 행동

스텝 종료 시 `docs/PROGRESS.md`를 갱신한다. - 구현한 내용 - 배운 개념과
이해 상태 - 실행 명령 및 실제 결과 - 정상/오류/경계 테스트 결과 - 아직
헷갈리는 점 - 변경된 파일 - Git 커밋(있다면) - 다음에 할 단 하나의
구체적인 작업

**스텝 상태는 다음과 같이 구분한다.** - `미착수` - `진행 중` -
`구현 완료` - `검증 완료` - `독립 수행 확인`

`검증 완료`는 기능 테스트를 통과했다는 뜻이다. `독립 수행 확인`은
학습자가 핵심을 설명하고 작은 변경을 도움 없이 수행했다는 뜻이다. 두
상태를 혼동하지 않는다.

## 3. 학습 지원 단계: 너무 쉽게도, 너무 어렵게도 하지 않기

막혔을 때 정답을 바로 던지거나 반대로 오래 방치하지 않는다. 다음 순서로
지원한다.

1.  **관찰 질문:** 실제로 어떤 결과가 나왔는지 확인한다.
2.  **힌트:** 어떤 개념 또는 줄을 살펴볼지 알려준다.
3.  **부분 예제:** 어려운 부분만 작은 코드로 보여준다.
4.  **완성 예제:** 필요하면 작동하는 예시를 제공하고, 각 부분의 역할을
    설명한다.
5.  **변형 실습:** 값이나 조건을 바꿔 학습자가 직접 실행한다.
6.  **미션 적용:** 최종 코드에 적용하고 테스트한다.

학습자가 명확히 좌절하거나 개념을 놓친 경우에는 난도를 낮추고 더 작은
실험으로 돌아간다. 같은 설명을 더 길게 반복하는 것만으로 해결하려 하지
않는다.

## 4. 프로젝트 구조와 각 파일의 역할

구조는 목표안이며, 모든 파일을 첫날에 만들지 않는다. 필요할 때 하나씩
추가한다.

``` text
codyssey-mission2-1/
├── mission_file/                       # 공식 미션 원문
├── docs/
│   ├── STUDY_AND_IMPLEMENTATION_PLAN.md # 이 운영 계획
│   ├── PROGRESS.md                     # 실제 진행 상태
│   ├── REQUIREMENTS_TRACE.md           # 요구사항-구현-검증 추적표
│   ├── CONCEPT_CHECKLIST.md            # Python 개념 숙련도
│   └── DECISIONS.md                    # 설계 선택과 이유
├── practice/                           # 개념을 분리해 실험하는 공간
├── budget_app/
│   ├── __init__.py
│   ├── __main__.py                     # python -m budget_app 진입점
│   ├── cli.py                          # 명령어/인자/입출력
│   ├── models.py                       # Transaction 등 데이터 구조
│   ├── repository.py                   # 파일 I/O
│   ├── services.py                     # 업무 규칙
│   └── decorators.py                   # 로그/시간 측정 등
├── data/
│   ├── transactions.jsonl
│   ├── categories.jsonl
│   └── budgets.jsonl
├── tests/
└── README.md
```

파일 분리는 목적이 아니라 책임을 명확하게 하기 위한 수단이다. 미션에서
요구하는 최소 3개 모듈과 2개 이상의 클래스는 충족하되, 이해 없이 파일만
많이 만드는 것을 피한다. 초기에는 한두 파일로 개념을 익히고, 모듈 분리
단계에서 역할을 나눈다.

## 5. 단계별 학습·구현 로드맵

60시간은 미션의 기준 학습시간이지 모든 사람에게 보장되는 완료 시간은
아니다. 아래 시간은 진행을 돕는 **대략적인 배분**이다. 이해가 부족하면
보충 시간을 쓰고, 이미 이해한 내용은 간단히 확인하고 넘어간다.

### Step 0 --- 미션 해석과 개발환경

**목표:** 요구사항, 실행 환경, 현재 프로젝트 상태를 확인한다.

학습/실행: - 미션을 기능·데이터·구조·품질 요구사항으로 분류 - Python
3.10 이상 버전 확인 - 프로젝트 루트, 파일/폴더, 터미널 명령 확인 - Git
상태와 `.gitignore` 확인 - 개인 데이터가 포함될 수 있는 `data/`의 공개
여부 결정

완료 증거: - 모든 필수 요구사항이 추적표에 등록됨 - 프로젝트 루트에서
Python 명령 실행 가능 - 현재 폴더/파일 상태를 정확히 기록

### Step 1 --- 출력, 변수, 자료형, 연산

**미션 연결:** 메뉴 출력, 금액, 수입·지출 계산.

개념: - `print()`, 주석, 변수와 대입 - `int`, `float`, `str`, `bool`,
`None` - 연산자, 연산 우선순위, 형 변환 - 문자열과 숫자의 차이,
f-string - 이름 짓기와 읽기 쉬운 코드

실습 → 적용: - 콘솔 메뉴 출력 - 수입/지출 금액을 변수로 계산 - 문자열과
정수 연산의 차이 관찰 - 실제 가계부의 금액 처리와 연결

검증: - 계산 결과 확인 - 자료형을 말로 구분 - 값이나 계산식을 바꿔 실행

### Step 2 --- 입력, 조건문, 반복문

**미션 연결:** 대화형 `add`, 입력 검증과 재입력.

개념: - `input()`은 문자열을 반환함 - `if / elif / else`, 비교·논리
연산자 - `for`, `while`, `range`, `break`, `continue` - 들여쓰기와 코드
블록 - 재입력 루프

실습 → 적용: - 거래 타입 입력 - 금액 입력 및 양수 정수 검증 -

**중요한 설계 판단:** 제너레이터로 파일을 순차 읽는 것과 결과를

선택지는 (1) 파일을 최신순으로 유지하는 저장 정책, (2) 전체 정렬을 위한
메모리 사용을 명시하는 방식 등이다. 요구사항을 숨기지 않고 선택의 메모리
특성과 데이터 무결성을 설명한다. 어떤 방식을 선택했는지는
`DECISIONS.md`에 기록한다.

## 9. Git 운영 규칙

-   의미 있는 작은 변경 단위로 커밋한다.
-   커밋 전 `git status`와 `git diff`를 확인한다.
-   예시:
    -   `docs: add learning and implementation plan`
    -   `practice: add input and calculation exercises`
    -   `feat: add transaction model`
    -   `feat: persist transactions as JSONL`
    -   `test: cover invalid transaction inputs`
    -   `fix: preserve data during transaction deletion`
-   Git을 단순 명령 암기로 가르치지 않는다. working tree, staging area,
    commit이 실제로 어떤 상태인지 프로젝트에서 확인한다.
-   `.gitignore`에 필요한 파일을 명시한다.
-   `data/`에는 실제 개인 거래 내역이 들어갈 수 있으므로 공개 저장소에
    올리지 않는 것을 기본으로 한다. 필요한 경우 가짜 테스트 데이터만
    공유한다.
-   비밀번호, API 키, 토큰, 개인정보를 커밋하지 않는다.
-   push가 성공했는지 실제 원격 저장소 상태를 확인한다.

## 12. AI 튜터 응답 규약

작업을 진행할 때 튜터는 가능한 한 다음 순서를 따른다.

1.  **현재 위치:** 어느 스텝인지 짧게 확인
2.  **목표:** 이번 작업과 연결된 미션 요구사항
3.  **개념:** 초보자용 설명과 작은 예제
4.  **직접 행동:** 사용자가 작성·실행할 코드와 명령
5.  **예상 결과:** 성공했을 때의 출력 또는 관찰점
6.  **미션 적용:** 실제 애플리케이션의 어느 부분에 연결할지
7.  **검증:** 정상/오류/경계 테스트
8.  **진행 기록:** 무엇을 기록하고 다음에 할 작업

이 형식을 매번 긴 양식으로 보여 줄 필요는 없다. 간단한 작업에서는 짧게
유지하되, 실제 코딩·실행·미션 적용·검증이라는 핵심 요소를 빼지 않는다.

튜터는 다음을 하지 않는다. - 실행하지 않은 코드를 실행 성공했다고
말하기 - 실제 요구사항을 확인하지 않고 필수 조건을 만들어내기 - 개념
퀴즈만 내고 직접 코딩을 생략하기 - 모든 코드를 한 번에 대신 완성해
학습자의 수행을 없애기 - 학습자가 막혔는데 같은 설명만 반복하기 -
테스트가 실패했는데도 다음 기능으로 진행하기 - 문서에 기록되지 않은 진행
상태를 기억한다고 단정하기

## 부록 B. 미션 밖으로 벗어나지 않기

보너스 기능(백업, 반복 내역, 테이블 출력 등)은 필수 요구사항을 검증한
