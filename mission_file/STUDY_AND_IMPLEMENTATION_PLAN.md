## Python과 Git 심화 --- 나만의 용돈 기입장 프로그램

-   문서 버전: 1.0
-   대상: Python 초보 학습자
-   목표: 미션을 완성하는 과정에서 Python의 핵심 개념을 직접 실습하고,
    설명하고, 검증할 수 있게 한다.
-   프로젝트 폴더 예시: `codyssey-mission2-1/`

-   데이터 저장 형식: JSONL

## 1. 이 문서의 목적

이 문서는 단순한 공부 계획표가 아니다. **학습 방법, 구현 순서, 검증
기준, 진행 기록, 컨텍스트 복구 절차**를 함께 정의하는 프로젝트 운영
문서다.

대화가 길어지거나 새 대화로 넘어가더라도 이 문서를 기준으로 현재 위치를
확인하고 다음 스텝을 다시 구성한다. 단, 실제 진행 상태는 이 문서만 보고
추측하지 않는다. 완료한 단계와 검증 결과를 `docs/PROGRESS.md`에
기록하고, GitHub의 코드 및 테스트 결과와 대조한다.

### 핵심 원칙

1.  **개념 → 직접 실행 → 미션 적용 → 검증 → 설명·재구성**을 하나의 학습
    사이클로 삼는다.
2.  설명만 듣거나 코드를 복사하는 것으로 스텝을 완료 처리하지 않는다.
3.  모든 실습은 최종 미션의 실제 요구사항과 연결한다.
4.  작은 기능을 구현할 때마다 테스트하고, 기존 기능이 깨지지 않았는지
    회귀 검증한다.
5.  코드가 동작하는 것과 학습자가 이해하는 것을 별도로 확인한다.
6.  모르는 부분은 숨기지 않고 기록한 뒤, 작은 실험으로 원인을 확인한다.
7.  한 번에 많은 개념을 몰아넣지 않는다. 필요한 순간에 배우되, 필수 개념
    목록을 기준으로 누락 여부를 추적한다.
8.  먼저 동작하는 최소 버전을 만든 뒤 안전성·가독성·구조를 단계적으로
    개선한다. 처음부터 완벽한 설계를 요구하지 않는다.
9.  Git은 최종 제출 직전에만 쓰지 않고, 작고 의미 있는 변경마다
    사용한다.
10. 미션 원문이 최우선 기준이다. 문서와 미션 요구사항이 충돌하면 미션
    원문을 우선하고, 문서를 갱신한다.

## 2. 매 스텝의 표준 학습 절차

각 스텝은 아래 절차를 모두 포함해야 한다. 필요한 경우 한 절차를 여러
개의 짧은 실습으로 나눌 수 있다.

### A. 목표와 미션 연결

-   이번에 구현할 기능 또는 해결할 문제를 한 문장으로 설명한다.
-   해당 기능이 미션의 어느 요구사항을 만족시키는지 표시한다.
-   완료 후 사용자가 프로그램에서 무엇을 할 수 있게 되는지 예측한다.

### B. 초보자용 개념 설명

-   전문 용어를 먼저 나열하지 않고, 일상적인 비유와 작은 예제로
    설명한다.
-   새 용어가 나오면 쉬운 정의와 실제 코드에서의 역할을 함께 제공한다.
-   문법의 모양뿐 아니라 **왜 필요한지, 언제 사용하는지, 없으면 어떤
    문제가 생기는지**를 설명한다.
-   기존에 배운 개념과 연결한다.
-   개념 설명은 짧게 나누고, 긴 설명을 한 번에 몰아서 제공하지 않는다.

### C. 실행 가능한 작은 실험

-   학습자가 직접 입력할 코드를 제공하거나 일부를 직접 작성하게 한다.
-   실행 명령과 예상 출력을 명확히 제시한다.
-   출력이 다르면 무작정 다음으로 넘어가지 않고 차이를 확인한다.
-   값을 바꾸거나 일부 코드를 제거하는 등 작은 변형 실험을 포함한다.
-   실험 결과를 보고 학습자가 관찰한 사실을 자기 말로 설명하도록
    유도한다.

### D. 실제 미션에 적용

-   연습용 예제만 만들고 끝내지 않는다.
-   연습에서 배운 개념을 `budget_app/`의 실제 기능에 적용한다.
-   연습 코드와 실제 코드가 어떻게 연결되는지 짚어 준다.
-   같은 코드를 불필요하게 두 번 작성하지 않는다. 연습용 코드는 개념을
    분리해 확인하기 위한 것이고, 최종 기능은 애플리케이션 코드에
    구현한다.

### E. 검증

-   최소 한 가지 정상 입력과 한 가지 잘못된 입력 또는 경계 조건을
    확인한다.
-   기능에 적합한 자동 테스트를 추가하거나, 아직 테스트를 배우기 전에는
    재현 가능한 수동 테스트 절차를 기록한다.
-   기존 기능에 영향을 줄 수 있으면 회귀 테스트를 실행한다.
-   요구사항 추적표에 구현 상태와 검증 증거를 남긴다.

### F. 이해 확인과 독립 수행

-   학습자가 코드의 핵심 부분을 자기 말로 설명한다.
-   코드 일부를 가리고 직접 완성하거나, 작은 변형 문제를 해결한다.
-   도움 없이 비슷한 코드를 다시 작성하는 것은 필요에 따라 수행한다. 단,
    매번 전체 코드를 처음부터 외우게 하지 않는다.
-   답을 맞히는 퀴즈만으로 실습을 대체하지 않는다.

### G. 진행 기록

스텝 종료 시 `docs/PROGRESS.md`에 다음을 기록한다. - 완료한 작업 -
실행한 명령 - 검증한 사례와 결과 - 이해한 개념 - 아직 헷갈리는 점 - Git
커밋 해시 또는 커밋 메시지(커밋했다면) - 다음에 시작할 정확한 작업

**완료 기준:** 코드가 실행됨 + 미션 요구사항과 연결됨 + 검증함 + 핵심
개념을 설명하거나 직접 변형할 수 있음. 진행 상황에 따라 일부 항목은
`진행 중`으로 남기고, 완료했다고 과장하지 않는다.

## 3. 프로젝트 구조

처음부터 모든 파일을 만들지 않는다. 단계가 필요로 할 때 하나씩 추가한다.

``` text
codyssey-mission2-1/
├── mission_file/                 # 공식 미션 원문
├── docs/
│   ├── STUDY_AND_IMPLEMENTATION_PLAN.md  # 이 문서
│   ├── PROGRESS.md               # 실제 진행 기록
│   ├── REQUIREMENTS_TRACE.md     # 요구사항-구현-검증 연결표
│   └── DECISIONS.md              # 설계 결정 및 이유
├── practice/                     # 개념을 분리해 실험하는 작은 코드
├── budget_app/
│   ├── __init__.py
│   ├── __main__.py               # python -m budget_app 진입점
│   ├── cli.py                    # 명령어/인자/사용자 입출력
│   ├── models.py                 # Transaction 등 데이터 구조
│   ├── repository.py             # 파일 읽기/쓰기
│   ├── services.py               # 업무 규칙과 기능 처리
│   └── decorators.py             # 로그/시간 측정/예외 처리 등

│   ├── categories.jsonl
│   └── budgets.jsonl
├── tests/

```

이 구조는 목표 구조다. 실제 구현 중 필요하면 파일 이름이나 책임을
조정하되, 변경 이유를 `docs/DECISIONS.md`에 기록한다. 모듈 분리 자체가
목적이 되지 않게 한다.

## 4. 스텝별 학습·구현 로드맵

단계는 순서대로 진행하되, 검증 결과에 따라 앞 단계로 돌아갈 수 있다.
시간 배분은 고정 규칙이 아니라 60시간 미션을 위한 대략적인 계획이다.

### 0단계. 미션 해석과 개발환경 확인

**목표:** 무엇을 만들어야 하는지 정확히 알고 실행 환경을 확인한다.

학습·실행: - 미션 요구사항을 기능, 데이터, 구조, 품질 조건으로
분류한다. - 터미널의 현재 폴더와 Python 버전을 확인한다. - 파일·폴더
생성, 현재 경로, 실행 명령을 연습한다. - Git 저장소 상태와
`.gitignore`를 확인한다. - 저장 파일에 실제 사용자 데이터가 들어갈 수
있으므로 생성 데이터와 코드의 버전 관리 정책을 정한다.

검증: - Python 3.10 이상인지 확인한다. - 프로젝트 루트에서 명령을 실행할
수 있다. - 미션 요구사항 추적표의 모든 필수 항목이 등록돼 있다.

### 1단계. 출력, 변수, 자료형, 계산

**미션 연결:** 가계부의 메뉴, 금액, 잔액 계산.

개념: - `print()`, 주석, 변수와 대입 - 정수 `int`, 문자열 `str`, 실수
`float`, 불리언 `bool` - 연산자와 연산 우선순위 - 문자열과 숫자의 차이,
형 변환 - 변수 이름과 읽기 쉬운 코드

실습: - 프로그램 제목과 메뉴 출력 - 수입·지출 금액을 변수로 두고 잔액
계산 - 금액을 문자열로 더할 때와 정수로 계산할 때 차이를 확인

검증: - 정상적인 금액으로 계산 결과 확인 - `int`와 `str`의 차이를 설명 -
계산식을 바꾸고 결과를 예측한 뒤 실행

### 2단계. 입력, 조건문, 반복문

**미션 연결:** 대화형 `add`, 메뉴 흐름, 입력 오류 처리.

개념: - `input()`은 문자열을 반환한다는 점 - `if / elif / else`,
비교·논리 연산자 - `for`, `while`, `range` - `break`, `continue` -
들여쓰기와 코드 블록 - 입력값 검증과 재입력 흐름

실습: - 수입/지출 유형 입력 - 잘못된 유형이면 오류 메시지 출력 - 금액이
양의 정수인지 검증 - 카테고리 목록에 있는 값인지 확인

검증: - 정상 입력, 빈 입력, 잘못된 유형, 0, 음수, 숫자가 아닌 값 시험 -
잘못된 입력에도 프로그램이 의도대로 계속되거나 안전하게 종료되는지 확인

### 3단계. 컬렉션과 데이터 다루기

**미션 연결:** 태그, 거래 목록, 카테고리, 월별 집계.

개념: - `list`, `tuple`, `dict`, `set` - 인덱스와 슬라이싱 - `append`,
`remove`, `in` - 딕셔너리의 키와 값, 안전한 조회 - 중첩 데이터 구조 -
가변 객체와 참조의 기초 - 정렬, `sorted`, `key` - `enumerate`, `zip`이
필요한 경우

실습: - 거래 여러 건을 리스트로 표현 - 거래 한 건을 딕셔너리로 표현 -
카테고리별 지출을 딕셔너리로 집계 - 태그 목록에서 특정 태그 검색 - 최신
날짜순 정렬

검증: - 빈 목록, 중복 카테고리, 없는 키, 같은 날짜의 거래를 확인 -
리스트와 딕셔너리를 언제 쓰는지 설명

### 4단계. 함수와 책임 분리

**미션 연결:** add/list/search/summary에 필요한 처리 함수.

개념: - `def`, 매개변수, 인수, `return` - 지역 변수와 전역 변수 - 기본
인수, 키워드 인수 - 반환값과 `print()`의 차이 - 함수의 단일 책임 - 순수
함수의 기초와 부작용 - 간단한 문서 문자열(docstring)

실습: - 금액 검증 함수 - 날짜 검증 함수 - 거래를 화면에 표시하는 함수 -
카테고리별 합계를 계산하는 함수

검증: - 같은 입력이면 기대한 반환값이 나오는지 확인 - 함수가 계산과
출력/파일 저장을 뒤섞지 않도록 점검 - 함수의 입력과 반환값을 말로 설명

### 5단계. 예외 처리와 안전한 입력

**미션 연결:** 잘못된 입력, 파일 오류, 스택트레이스 대신 도움말 제공.

개념: - 예외와 오류의 차이 - `try / except / else / finally` - 구체적인
예외 유형을 잡는 이유 - `raise`로 오류를 알리는 방법 - 사용자에게 보여
줄 오류와 개발 중 진단 정보의 구분

실습: - 숫자 변환 실패 처리 - 날짜 형식 오류 처리 - 파일
없음/권한/잘못된 데이터 처리 - 원인과 해결 힌트를 출력하고 비정상 종료
코드 반환

검증: - 잘못된 입력에서 스택트레이스가 사용자 화면에 노출되지 않는지
확인 - 오류가 조용히 무시되지 않는지 확인 - 정상 종료 코드 0, 오류 종료
코드 0이 아닌 값 확인

### 6단계. 파일 입출력과 JSON/JSONL

**미션 연결:** 거래·카테고리·예산을 프로그램 종료 후에도 보존.

개념: - 파일 경로와 현재 작업 디렉터리 - `open`, `with`, 파일 모드와
인코딩 - 텍스트 파일 읽기/쓰기 - JSON 객체와 JSONL 한 줄 레코드의 차이 -
`json` 모듈 - `pathlib.Path` - 파일이 없는 최초 실행 처리 - 저장 실패와
데이터 손상 고려

실습: - 거래 한 건을 JSONL 한 줄로 저장 - 여러 줄을 다시 읽기 -
`transactions.jsonl`, `categories.jsonl`, `budgets.jsonl` 분리 - 임시
파일을 이용해 안전하게 교체하는 기초 실습

검증: - 프로그램 종료 후 다시 실행해도 데이터가 남음 - 빈 파일, 파일
없음, 잘못된 JSON 한 줄 처리 - UTF-8 한글 메모가 깨지지 않음 - 세 종류의
데이터가 서로 다른 파일에 저장됨

### 7단계. 클래스, dataclass, 타입 힌트

**미션 연결:** 데이터 구조와 모듈 사이의 계약을 명확히 함.

개념: - 클래스와 인스턴스의 차이 - 속성과 메서드 - `__init__`의 역할 -
`dataclass` - 타입 힌트: `str`, `int`, `list[str]`, `dict`, `Optional`
또는 `| None` - 반환 타입과 매개변수 타입 - 타입 힌트는 자동으로 모든
값을 검증해 주는 기능이 아니라는 점

실습: - `Transaction` dataclass 만들기 - ID, 타입, 날짜, 양수 금액,
카테고리, 메모, 태그 표현 - JSON 데이터와 객체 간 변환 - 최소 2개 이상의
클래스를 사용하도록 설계

검증: - 유효한 거래 생성 - 잘못된 데이터가 어디에서 차단되는지 확인 -
타입 힌트가 함수 사용 방법을 어떻게 명확하게 하는지 설명

### 8단계. 모듈과 패키지, CLI

**미션 연결:** `python -m budget_app <command> [options]` 실행 구조.

개념: - 모듈과 패키지 - `import`와 `__init__.py` -
`if __name__ == "__main__":` - `__main__.py` - 함수와 클래스의 책임
분리 - `argparse`로 명령어·옵션 처리 - `--help`, 기본값, 필수 인자, 선택
인자 - 종료 코드

실습: - `python -m budget_app --help` - 하위 명령 `add`, `list`,
`search` 등의 명령 구조 만들기 - 옵션 이름을 `--` 형식으로 통일 - CLI는
입력/출력을 맡고 업무 규칙은 서비스 계층에 둠

검증: - 프로젝트 루트에서 모듈 실행 성공 - 각 명령의 `--help` 동작 -
필수 옵션 누락 시 이해 가능한 오류 출력

### 9단계. 저장소 계층과 스트리밍 제너레이터

**미션 연결:** list/search에서 파일 전체를 한 번에 메모리에 올리지 않기.

개념: - 저장소(repository)의 책임 - 반복 가능한 객체와
반복자(iterator) - `yield`와 `return`의 차이 - 제너레이터가 값을 한 번에
하나씩 전달하는 방식 - 메모리 사용량과 스트리밍 - `sorted()`는 전체
정렬을 위해 데이터를 모아야 할 수 있다는 점 - 최신순 출력 요구와
스트리밍 요구가 충돌할 때의 설계 선택

실습: - JSONL 파일을 한 줄씩 읽는 제너레이터 구현 - 검색 조건을 만족하는
거래만 yield - `--limit`에 따라 필요한 결과만 출력 - 최신순 정렬 요구를
충족하기 위해 어떤 접근이 가능한지 비교하고 설계 결정 기록

검증: - 전체 파일을 한 번에 `read()`/`readlines()`로 읽지 않는지 코드
검사 - 큰 파일을 가정한 테스트 - 최신순 결과와 `--limit` 동작 확인

중요: 파일을 한 줄씩 읽는 것과 결과를 최신순으로 정렬하는 것은 별개의
문제다. 정렬하려면 전체 데이터를 모아야 할 수 있다. 이 제약을 숨기지
않고 요구사항을 충족하는 구현과 메모리 특성을 함께 설명한다.

### 10단계. 거래 추가와 목록 조회

**미션 연결:** 첫 번째로 완성할 실제 end-to-end 기능.

개념: - 데이터 모델 → 서비스 → 저장소 → CLI의 흐름 - ID 생성 전략 - 날짜
형식 검증 - 양의 정수 금액 검증 - 등록된 카테고리 검사

실습: - 대화형 `add` - 거래를 영구 저장 - 저장된 거래를
`list --limit N`으로 조회

검증: - 저장 성공 메시지와 ID 출력 - 잘못된 입력 재요청 또는 명확한
오류 - 종료 후 재실행해도 거래가 존재 - 목록이 최신순이고 limit이 적용됨

### 11단계. 수정과 삭제(CRUD 완성)

**미션 연결:** `update`, `delete --id`.

개념: - CRUD의 의미 - 레코드 식별 - 원본 파일과 임시 파일 - 안전한
교체와 실패 시 데이터 보존 - 없는 ID 처리

실습: - update는 **옵션 방식**으로 고정한다. -
`update --id ... [--date ...] [--type ...] [--category ...] [--amount ...] [--memo ...] [--tags ...]` -
`delete --id ...` - 임시 파일 작성 후 원자적 교체를 적용할 수 있도록
설계

검증: - 정상 수정/삭제 - 없는 ID 수정/삭제 - 수정·삭제 중 오류가
발생해도 원본 데이터가 손상되지 않는지 확인 - 수정 후에도 모든 거래
데이터 형식이 유효한지 확인

### 12단계. 검색

비교 - 제너레이터로 조건별 결과 전달

실습: - `--from`, `--to`, `--category`, `--type`, `--q`, `--tag` - 여러
조건을 동시에 지정했을 때 모두 만족하는 결과 출력

검증: - 조건 하나씩과 복수 조건 조합 - 결과 없음 - 경계 날짜 포함 여부 -

### 13단계. 월별 요약과 예산

**미션 연결:** summary 및 budget 명령.

검증: - 데이터가 있는 달과 없는 달 - 수입만 있는 달, 지출만 있는 달 -

## 7. Git 사용 원칙

-   의미 있는 작은 변경 단위로 커밋한다.
-   예시 커밋 메시지:
    -   `docs: add mission learning plan`
    -   `practice: add basic input and calculation exercises`
    -   `feat: add transaction model`
    -   `feat: persist transactions as JSONL`
    -   `test: cover invalid transaction inputs`
    -   `fix: preserve data during transaction deletion`
-   커밋 전 `git status`와 `git diff`를 확인한다.
-   `data/`에 개인 거래 정보가 들어갈 수 있다. 공개 저장소에는 실제
    개인정보가 담긴 데이터를 올리지 않는다. 테스트용 샘플 데이터만
    사용하고, 저장 파일을 추적할지 여부를 명시적으로 결정한다.
-   비밀키, 토큰, 비밀번호 등은 절대 커밋하지 않는다.
-   Git 명령은 단순히 복사하는 것이 아니라 working tree, staging area,
    commit이 각각 무엇인지 실제 상태와 연결해 배운다.

## 8. 진행 기록 템플릿

`docs/PROGRESS.md`를 다음 형식으로 관리한다.

``` markdown
# Progress

## 현재 상태
- 마지막 완료 스텝:
- 현재 진행 중인 스텝:
- 다음에 시작할 정확한 작업:
- 마지막 검증 결과:
- 마지막 커밋:

## 완료 기록
### YYYY-MM-DD — Step N: 제목
- 구현:
- 학습한 개념:
- 실행 명령:
- 검증한 정상 사례:
- 검증한 오류/경계 사례:
- 테스트 결과:
- 아직 헷갈리는 점:
- 다음 작업:
```

작업을 실제로 하지 않았으면 완료로 기록하지 않는다. 대화가 바뀐 뒤에는
이 파일과 실제 코드·Git 상태를 먼저 확인하고 이어간다.

## 9. 컨텍스트 복구 프로토콜

새 대화나 컨텍스트 전환 후에는 아래 순서로 재개한다.

1.  GitHub 저장소의 `STUDY_AND_IMPLEMENTATION_PLAN.md`를 확인한다.
2.  공식 미션 원문을 확인한다.
3.  `docs/PROGRESS.md`에서 마지막으로 검증된 스텝을 확인한다.
4.  `docs/REQUIREMENTS_TRACE.md`에서 미완료 또는 검증되지 않은
    요구사항을 확인한다.
5.  실제 코드와 테스트, Git 상태를 비교한다. 문서 기록과 실제 상태가
    다르면 실제 상태를 확인하고 기록을 수정한다.
6.  학습자에게 이미 이해한 내용을 불필요하게 처음부터 반복하지 않는다.
    다만 짧은 실행이나 설명으로 핵심 이해를 확인할 수 있다.
7.  다음 한 가지 구체적인 작업을 제시한다. 한 번에 전체 코드를
    작성하거나 많은 과제를 나열하지 않는다.
8.  새롭게 결정한 설계나 바뀐 요구사항은 관련 문서에 기록한다.

**중요한 제한:** 이 문서는 컨텍스트 복구를 돕는 기준 자료이지, 그 자체가
자동으로 GitHub에 접근하거나 최신 상태를 보장하는 장치는 아니다. 새
대화에서는 저장소 URL이나 관련 파일을 제공하거나, 연결된 GitHub 도구로
저장소를 조회할 수 있어야 한다. 확인하지 못한 진행 상황을 기억한다고
주장하지 않는다.

## 10. AI 튜터의 행동 규칙

AI 튜터는 다음 규칙을 지킨다.

-   매번 현재 스텝과 미션 연결점을 명확히 한다.
-   초보자가 이해하지 못한 상태에서 새 개념을 연달아 추가하지 않는다.
-   정답 코드를 처음부터 통째로 제공하기보다 작은 실행 가능한 단위로
    함께 만든다.
-   다만 학습자가 직접 코딩할 수 있도록 필요한 코드, 실행 명령, 예상
    출력은 충분히 제공한다.
-   학습자가 코드를 직접 입력하고 실행하도록 유도한다.
-   실행 결과를 확인하기 전에 성공했다고 단정하지 않는다.
-   오류가 나면 전체 코드를 다시 던지기보다 원인 후보를 좁히고 최소한의
    수정으로 해결한다.
-   모든 연습은 최종 애플리케이션에 적용하거나, 적용하지 않는 이유를
    설명한다.
-   구현 여부와 이해 여부를 구분해서 기록한다.
-   요구사항을 지속적으로 검증하며, 테스트가 통과하지 않으면 다음
    기능으로 성급히 넘어가지 않는다.
-   필요할 때 개념을 다시 설명하되, 같은 설명을 무의미하게 반복하지
    않는다.
-   `practice/`는 실험 공간, `budget_app/`는 실제 애플리케이션으로
    구분한다.
-   Python 3.10 이상과 표준 라이브러리만 사용한다.
-   미션 원문에 없는 기능을 필수인 것처럼 추가하지 않는다.
-   사용자가 학습 방법을 수정하자고 하면 문서와 진행 방식을 함께
    조정한다.

## 11. 첫 시작 지점

현재 알고 있는 사실: - 미션은 Python 기반 파일 입출력 콘솔 가계부다. -
공식 요구사항에는 거래 추가/목록/검색/월별
요약/예산/카테고리/수정/삭제/CSV import-export가 포함된다. - JSONL 또는
CSV 중 하나를 선택해야 하며, 본 계획은 JSONL을 선택한다. -
`practice/`에서 개념을 실험하고, 배운 내용을 `budget_app/`에 적용하는
방식을 사용한다. - 실제 현재 파일과 구현 상태는 작업을 시작할 때
확인해야 한다.

첫 작업: 1. 이 문서를 `docs/STUDY_AND_IMPLEMENTATION_PLAN.md`로
저장한다. 2. `docs/PROGRESS.md`와 `docs/REQUIREMENTS_TRACE.md`를 만든다.
3. Git 상태를 확인하고 문서 변경을 커밋한다. 4. 공식 미션 요구사항을
추적표와 대조한다. 5. Python 버전과 프로젝트 경로를 확인한 뒤 Step 0부터
진행한다.

첫 기능부터 완성하려 하지 않는다. **작게 만들고, 직접 실행하고, 실제
미션에 연결하고, 검증한 다음에 다음 단계로 간다.**
